## תרגיל 4: ציד המפתח שדלף (אבטחה - 15 דקות)
### הנחיות:
נתון קובץ frontend קטן של חנות אונליין לעוגות. קובץ כזה נשלח לדפדפן של כל מבקר. מצאו בו את כל הבעיות הקשורות לסודות, והסבירו מה הייתם עושים. כל המפתחות בקובץ מומצאים ולא אמיתיים.

**index.html:**
```html
<!DOCTYPE html>
<html lang="he" dir="rtl">
<head><meta charset="UTF-8"><title>עוגות של רונית</title></head>
<body>
  <h1>הזמנת עוגה</h1>
  <input id="name" placeholder="שם">
  <button onclick="sendOrder()">שלחו הזמנה</button>

  <script>
    // Supabase - public key meant for the browser
    const SUPABASE_URL = "https://fakeproject.supabase.co";
    const SUPABASE_ANON_KEY = "FAKE_public_key_1234567890";

    // Service key - full access to the database
    const SUPABASE_SERVICE_KEY = "FAKE_service_key_abcdefghijklmnop";

    // Claude API key for the order summary
    const ANTHROPIC_API_KEY = "FAKE_sk-ant-0000000000000000";

    // WhatsApp token
    const WHATSAPP_TOKEN = "FAKE_whatsapp_token_999";

    async function sendOrder() {
      const name = document.getElementById("name").value;
      await fetch(SUPABASE_URL + "/rest/v1/orders", {
        method: "POST",
        headers: { apikey: SUPABASE_SERVICE_KEY, "Content-Type": "application/json" },
        body: JSON.stringify({ name })
      });
    }
  </script>
</body>
</html>
```

### שאלות:
1. אילו מהמפתחות אסור שיופיעו בקובץ הזה? ואיזה מותר, ולמה?
2. מה היה יכול לקרות אם מבקר היה פותח DevTools ולשונית Sources, או לוחץ על View Source?
3. איפה צריכים לשמור את המפתחות הסודיים, ואיזו שכבה צריכה להשתמש בהם?
4. נניח שהמפתח היה אמיתי והעלינו אותו לאתר חי. אילו שני צעדים חייבים לעשות מיד?
5. בקשו מ-Claude Code לתקן את הקובץ כך שהסודות יעברו ל-backend או לקובץ dot env. בדקו שהתיקון לא השאיר מפתח סודי בקוד הלקוח.

## הנחיות למרצה

### תרגיל 1
תשובה טובה: הבקשה הראשונה היא בדרך כלל מסמך ה-HTML (GET, סטטוס 200). קבצי CSS ו-JS מופיעים בסוגים Stylesheet ו-Script. בקשות לדומיין אחר (פונטים, אנליטיקס, Supabase) הן בקשות לצד שלישי. סטטוס 404 על favicon הוא מקרה נפוץ ותמים. תשובה מ-Supabase היא בדרך כלל JSON. אם אין אתר, אפשר להשתמש בדף נחיתה מקומי.

### תרגיל 2
1. `https` / `www.my-clinic.co.il` / `/appointments/new` / `doctor=cohen&day=sunday`
2. `http` / `localhost:3000` / `/api/tasks` / `done=false` (3000 הוא מספר הפורט)
3. `https` / `abcd1234.supabase.co` / `/rest/v1/tasks` / `select=*&limit=10`

הכתובת השנייה אינה מאובטחת (http בלי s), אבל זה בסדר כי היא localhost. localhost מצביע על המחשב עצמו ולכן אף אחד אחר לא יכול לגשת אליה. `select=*` אומר "כל העמודות", `limit` מגביל את מספר השורות, ולכן עם `limit=2` יחזרו שתי שורות לכל היותר.

### תרגיל 3
תשובה טובה: Frontend: קבצי HTML/CSS/JS או רכיבי React שרצים בדפדפן. Backend: קוד שרת, או שכבת Supabase שמטפלת בהרשמה והרשאות. Database: טבלת המשימות ב-Supabase. המידע נשמר ב-database ולא בדפדפן. ההרשאה נבדקת בצד השרת או ב-database (למשל חוקי גישה ברמת שורה), ולא רק בכפתורים שמוסתרים ב-frontend, כי אפשר לעקוף אותם. שליחת וואטסאפ נעשית ב-backend כי היא דורשת מפתח סודי.

### תרגיל 4
- מותר בדפדפן: `SUPABASE_URL` ו-`SUPABASE_ANON_KEY` (מפתח ציבורי, ההגנה האמיתית באה מחוקי ההרשאות בבסיס הנתונים).
- אסור: `SUPABASE_SERVICE_KEY`, `ANTHROPIC_API_KEY`, `WHATSAPP_TOKEN`.
- בעיה נוספת בקוד: הבקשה ל-Supabase משתמשת במפתח השירות במקום במפתח הציבורי.
- כל מבקר יכול לקרוא את הקובץ, להעתיק את המפתחות ולהשתמש בהם: לקרוא ולמחוק את כל ההזמנות, לצרוך שימוש ב-AI על חשבונכם, לשלוח הודעות בשמכם.
- אם מפתח אמיתי דלף: לבטל אותו מיד ולייצר חדש (rotate), ולבדוק את יומני השימוש לגישה חריגה. מחיקה מהקוד אינה מספיקה, כי המפתח נשאר בהיסטוריה ובעותקים.
- תיקון טוב: קריאה ל-endpoint בצד השרת שמחזיק את המפתחות במשתני סביבה, ובדפדפן רק המפתח הציבורי. כדאי להדגיש שמשתנה סביבה שמוטמע בקוד ה-frontend בזמן הבנייה נחשף גם הוא.

### תרגיל 5
יש לוודא שהלומדים לא מקבלים את ההסבר כמובן מאליו: Claude Code עלול לטעות או להכליל, ולכן מאמתים מול הקבצים ו-DevTools. תשובה טובה לשאלה 3 ממפה, למשל בפרויקט הוואטסאפ: ה-webhook והשימוש במפתחות רצים בשרת, ואולי אין frontend כלל. בפרויקט המסמכים: טופס העלאה בדפדפן, עיבוד בשרת.
